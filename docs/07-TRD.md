# 07 — Technical Requirements Document (includes Component Architecture, Data Model, CMS notes)

## Stack decision
The stack stays **static HTML generated by a Node build script**. Reasons:
- The existing infrastructure works and is intentionally preserved: Cloudflare Pages running the `npm run build` build command, Decap CMS on a GitHub backend with a Cloudflare Worker for OAuth, and a `_posts/*.md` → `blog/*.html` pipeline.
- A framework (Next/Astro) would add hosting and CMS migration risk for no user-visible gain.
- Output is plain HTML, which is the fastest option and ideal for local SEO.

| Concern | Choice |
|---|---|
| Templating | Plain JS template literals in `src/` (no dependency) |
| Markdown | `gray-matter` + `marked` (unchanged from legacy) |
| Motion | GSAP 3.13 + ScrollTrigger, vendored (`assets/vendor/`), loaded `defer` |
| Images | `sharp` (dev-only) → AVIF/WebP at 480/960/1600 + JPEG fallback (`npm run images`) |
| CSS | Single `assets/css/main.css`, token-based, no framework |
| JS | `assets/js/core.js` (every page), `motion.js` (every page, GSAP), `booking.js`, `gallery.js`, `listing.js` (blog/FAQ filter). Page-specific scripts load only where needed |

## Directory
```
build.js              → generates every HTML page, sitemap.xml, posts.json, robots.txt, llms.txt
src/layout.js         → <head>, nav, footer, action bar, JSON-LD helpers
src/components.js     → picture(), icons, specimen label, CTA, booking composer, hours, FAQ list
src/icons.js          → custom SVG icon set
src/pages/*.js        → home, about, services-hub, service, gallery, faqs, blog-index, post, contact, 404
data/clinic.js        → NAP, hours, doctors, socials, areas (single source of truth)
data/services.js      → taxonomy, per-service photo, related links, short copy
data/photos.js        → curated real-photo manifest; photos.meta.json generated
data/extracted.json   → legacy long-form content (scripts/extract-content.js)
_posts/               → CMS markdown (copied verbatim from legacy)
admin/                → Decap CMS (unchanged)
images/p/             → generated responsive images
```

## Data model
- `clinic`: `{name, phone, phoneDisplay, whatsapp, address{street, locality, city, pin, landmark}, geo, mapsUrl, hours[{days, open, close}], closedDay, founded, fees, socials, areas}`
- `service`: `{slug, name, group, photo, blurb, related[], blogCat}`, plus extracted `{title, description, h1, lead, body, faqs}`
- `post` (front-matter, unchanged): `title, date, cat, catLabel, img, summary, read, slug?`

## Component architecture
- `layout({title, description, path, image, schema[], body, scripts[]})` produces the full document.
- `picture(id, {sizes, eager, class})` produces `<picture>` with AVIF/WebP `srcset`, width/height, focal `object-position`, the dominant-colour placeholder and alt text.
- `icon(name)` returns inline SVG (`aria-hidden`).
- `bookingComposer({id})` is reused on home and `/contact`.
- `faqList(items)` uses `<details>`/`<summary>` (native, accessible), with an optional FAQPage schema.

## Integrations (see conditional/19)
WhatsApp deep links, `tel:`, Google Maps link and click-to-load embed, GA4 `G-94PYDYSWKF`, Decap CMS.

## Security
- Static site with no secrets in the repository. The CMS OAuth worker URL is public config, as before.
- `_headers` adds `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` and `X-Frame-Options: SAMEORIGIN` (except `/admin`).
- No user data is stored; the booking form only builds a WhatsApp URL client-side.

## Build
- `npm run images` is run manually when photos change (slow, about 60 s).
- `npm run build` runs on Cloudflare Pages, needs no `sharp`, and completes in under 3 s.
